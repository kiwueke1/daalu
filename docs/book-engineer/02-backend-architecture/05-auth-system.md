# 5. Authentication — JWT, PATs, the auth gate

This chapter covers everything authentication-related: how
sessions are issued, how PATs work, where the gate lives,
how the executor's scope check is enforced, and how
webhooks-with-secrets fit in.

If you're investigating a 401 in production, this is the
chapter.

---

## The three credential types

Daalu accepts three credential types on incoming requests:

1. **JWT** — short-lived, signed, issued at login. Sent
   either as the `daalu_session` HttpOnly cookie or as
   `Authorization: Bearer <jwt>`.
2. **Personal access token (PAT)** — opaque, durable,
   prefix-recognizable (`dpat_…`). Sent as
   `Authorization: Bearer <pat>`.
3. **Ingest API key** — for webhook endpoints that have no
   user session. Sent as `X-Daalu-Key`. Different credential
   class entirely.

The browser uses JWT-in-cookie. Scripts use PATs. Webhooks
use ingest keys.

## JWT

### Issuance

`core/auth.py:issue_token` issues a JWT given a user_id and
tenant_id:

```python
def issue_token(*, user_id, tenant_id, is_admin) -> tuple[str, datetime]:
    settings = get_settings()
    expiry = datetime.now(tz=timezone.utc) + timedelta(
        minutes=settings.auth_token_ttl_min
    )
    payload = {
        "sub": user_id,
        "tenant_id": tenant_id,
        "is_admin": is_admin,
        "exp": int(expiry.timestamp()),
        "iat": int(datetime.now(tz=timezone.utc).timestamp()),
    }
    token = jwt.encode(payload, settings.auth_secret, algorithm="HS256")
    return token, expiry
```

Default TTL is 60 minutes. The frontend refreshes by calling
`/auth/me` periodically while active.

### Decode

`decode_token(token)` calls `jwt.decode` with the same secret
and algorithm; raises `TokenError` on any failure (expired,
malformed, wrong sig).

The auth gate uses `decode_token` for early validation. Route
handlers receive the user via `current_user`, which decodes
again *and* loads the user row.

### Storage

The JWT is delivered to the browser as a cookie:

```python
response.set_cookie(
    settings.auth_cookie_name,    # "daalu_session"
    token,
    httponly=True,
    secure=settings.auth_cookie_secure,    # True in prod
    samesite=settings.auth_cookie_samesite,  # "lax"
    expires=expiry,
)
```

Frontend JavaScript cannot read the cookie. XSS attacks are
denied access to the token; CSRF mitigations are SameSite +
the bearer-only API endpoints (everything that mutates state
also requires the user to authenticate).

## Personal access tokens (PATs)

### Format

```
dpat_<base64-url-safe(24 random bytes)>
```

Generated by `core/auth.py:generate_pat()`:

```python
PAT_PREFIX = "dpat_"

def generate_pat() -> str:
    return f"{PAT_PREFIX}{secrets.token_urlsafe(24)}"
```

24 random bytes → 32 character base64; with the prefix the
total is 37 characters. The prefix lets the auth gate
**cheaply distinguish a PAT from a JWT** before doing
expensive validation. JWTs start with `eyJ` (base64 of
`{"`). PATs start with `dpat_`.

### Storage

We store only the sha256 hash:

```python
def hash_pat(token: str) -> str:
    return hashlib.sha256(token.encode("utf-8")).hexdigest()
```

On creation, the cleartext is shown to the user **exactly
once**. Database leak → no usable tokens.

### Lookup

`api/deps.py:_resolve_pat`:

```python
async def _resolve_pat(token: str, db: AsyncSession) -> User:
    digest = hash_pat(token)
    stmt = select(PersonalAccessToken).where(PersonalAccessToken.token_hash == digest)
    pat = (await db.execute(stmt)).scalar_one_or_none()
    if pat is None:
        raise HTTPException(401, "invalid token")
    now = datetime.now(tz=timezone.utc)
    if pat.revoked_at is not None:
        raise HTTPException(401, "token revoked")
    if pat.expires_at is not None and pat.expires_at < now:
        raise HTTPException(401, "token expired")
    user = await db.get(User, pat.user_id)
    if user is None or not user.is_active:
        raise HTTPException(401, "user not found or inactive")
    try:
        pat.last_used_at = now
        await db.commit()
    except Exception:
        await db.rollback()
    return user
```

The `last_used_at` stamping is fire-and-forget; a failed
commit there must not break the request.

### Lifecycle

- **Create** — `POST /api/v1/auth/tokens` with name +
  optional expiry. Cleartext shown once.
- **List** — `GET /api/v1/auth/tokens`. Returns metadata
  only.
- **Revoke** — `DELETE /api/v1/auth/tokens/<id>`. Sets
  `revoked_at`. The token row stays in the DB for 7 days,
  then a background job hard-deletes it.

## Password hashing

`hash_password(plain)` uses bcrypt with a per-password salt.
We use the `passlib` library wrapped behind a thin façade so
we can swap algorithms if the cost factor needs raising.

`verify_password(plain, hashed)` is constant-time via
passlib.

We deliberately do **not** apply a global pepper. The
operational complexity of pepper rotation isn't worth the
marginal security upgrade at our threat model. If your
threat model demands it, the hook point is clear in
`core/auth.py:verify_password`.

## The executor scope

The Daalu executor (`daalu-executor` Deployment) authenticates
to itself with a JWT that carries an extra claim: `scope:
"executor"`. The gate in `core/auth.py`:

```python
EXECUTOR_SCOPE = os.environ.get("EXECUTOR_JWT_SCOPE", "executor")

def _require_executor_scope(payload: dict) -> None:
    if payload.get("scope") != EXECUTOR_SCOPE:
        raise PermissionError("executor scope required")
```

Write tools in `core/kube_tools.py` (and the analogous
SoT executor in `core/sot_executor.py`) call this gate before
running. The result: even if a user's JWT somehow ended up in
the executor's process, the gate would refuse to act on it
without the explicit `scope: executor` claim.

The JWT is issued at executor startup from an env-var secret
in the Helm chart's `templates/workers.yaml`. The chart pins
the scope value explicitly (rather than defaulting) so that an
ops-level secret rotation that omits the env var is loud, not
silently re-binding the identity gate.

## Ingest API keys

For webhook endpoints (`POST /api/v1/events`, the cluster
callback, the SoT webhooks), the caller doesn't have a user
session. We use a tenant-scoped ingest key instead.

The key is generated when the integration is created and
stored hashed. The auth gate bypasses the JWT/PAT check for
webhook paths (see Chapter 4) and the route handler does its
own HMAC verification:

```python
@router.post("/events")
async def ingest_event(request: Request, body: bytes = Body(...)):
    signature = request.headers.get("X-Daalu-Signature", "")
    tenant = await find_tenant_by_signature(body, signature)
    if not tenant:
        raise HTTPException(401)
    ...
```

The HMAC is computed over the body using the per-tenant
secret. Comparison is constant-time.

Routes that bypass auth entirely:

| Path | Reason |
|---|---|
| `/` | Frontend SPA bootstrap |
| `/health` | k8s liveness/readiness probes |

| `/docs`, `/redoc`, `/openapi.json` | API documentation |
| `/api/v1/auth/signup`, `/verify-email`, `/verify-email/resend` | Pre-session self-signup flow (flag-gated; neutral 202) |

Plus the webhook endpoints that authenticate via HMAC, and the
`*.cmtools.example.com` host bypass in `AuthGateMiddleware` (cmtools traffic is
authenticated by the tool proxy itself — chapter 68).

## Login modes: OIDC, native password, self-signup

Three **independent** switches govern who can log in and how
(`config.py:381-392`); getting their interaction right matters because prod
runs a non-obvious combination:

| Setting | Default | Prod | What it opens |
|---|---|---|---|
| `auth_mode` (`oidc`/`password`) | `password` | `oidc` | `oidc` renders "Sign in with Google" via **Keycloak** (`auth.example.com`, realm `daalu`) and stores `krt`/`kit` on the session for tool SSO |
| `native_password_login_enabled` (PR #88) | `false` | `true` | email+password **login** for operator-provisioned + invited users, *without* opening signup — `/login` works under `auth_mode=oidc` |
| `self_signup_enabled` (PR #85) | `false` | `false` (no SMTP at flip time; dark-deployed) | public `POST /auth/signup` + email verification; implies native login (back-compat) |

`/auth/config` advertises the resulting `password_login_enabled` /
`self_signup_enabled` so the login page renders the right controls
(`api/routers/auth.py:277-311`).

### Self-signup with email verification (PR #85, migration 0027)

`core/signup.py` creates an **isolated tenant** + an *inactive*, non-admin
user + an `EmailVerificationToken` (expiry `signup_token_expire_hours`,
default 48 h), reusing the invite token/email pattern. Routes:
`POST /auth/signup` (`auth.py:802`), `POST /auth/verify-email` (activates +
logs in, `auth.py:850`), `POST /auth/verify-email/resend` (`auth.py:897`).
Security posture: **neutral 202** on signup/resend (no email enumeration),
verification required before activation, `is_admin`/`is_superuser` hardcoded
false, full tenant isolation. Tests: `tests/test_auth_signup.py`.

Frontend: the login page renders SSO + local form + "Create an account";
`/signup` and `/verify-email` pages are on the public-route allowlist — and
so is the **`/accept-invite/` prefix** (PR #88): the authed app-shell used to
wrap invite links and fire authed API calls that 401'd, crashing the page
for the unauthenticated invitee.

### Outbound email (PR #86)

`core/notify.py:send_email` is plain `smtplib` over `SMTP_*` settings — any
SMTP relay works (e.g. **Resend**, `smtp.resend.com:587`, sender
`noreply@example.com`, with SPF/DKIM/DMARC on your zone), configured via the
SOPS-encrypted `daalu-automation-secrets`. Invites and signup verification both go through
it; `PUBLIC_BASE_URL=https://ops.example.com` builds the links. A send-only
API key is sufficient.

### SSO proper

Hub OIDC login (Keycloak brokered Google, identity mapping, cutover) is
[59. Keycloak hub SSO](../10-security/59-keycloak-hub-sso.md); operator
account provisioning and the seeded accounts are
